# rumo 0.3 — orchestrator, sonnet builders and /learn

Status: **implemented** on branch `feat/orquestrador-learn` (2026-10-13) — see §8 for where the
implementation diverged from this proposal; where they differ, the code wins. Base: rumo 0.2.0 (`521fcbb`) +
an analysis of `priyanshujha/subagent-studio` (`eae0e9a`, 2026-10-13).

## 1. Goal and premises

Three goals, in this tie-break order: **quality** (nothing ships without proof) → **economy**
(the expensive model only where it decides the outcome) → **speed** (parallel when it is safe).

Premises measured in subagent-studio (`docs/evidence.md`, one operator, mixed causes —
a direction, not a promise):

- 97% of tokens are cache re-reads → cost ≈ context size × number of requests.
  A lean main session is the biggest lever.
- A lean typed agent starts with ~20k of context; `general-purpose` with ~80k.
- Model/effort per role took cost per task from $30 → $7, with serious findings per change falling
  from 0.64 → 0.27.
- The final review finds a blocker/major in 9% of changes under 50 lines and in 33–38% above that.

What we do **not** copy: merging straight into main, a self-declared `Reviewed-by` trailer, a
post-review fix with no re-review, an unsupervised "allow everything" permission gate, effort
skills that work around a harness bug, agent twins with no difference in behavior.

## 2. The flow, end to end

```
 /rumo (align) ──► /rumo ticket ──► /rumo build #N ─────────────────────────────► PR → dev
   opus, 1 window     opus            orchestrator (opus medium, new window)
   + scout (haiku)                     │
                                       ├─ 1 PLAN     planner (opus high)  → plans/NNN.md
                                       ├─ 2 GATE     seams/risk → user approves (only if needed)
                                       ├─ 3 BUILD    waves of builders (sonnet high | opus medium)
                                       │             visual step → orchestrator inline
                                       ├─ 4 ACCEPT   orchestrator runs each step's Verify
                                       ├─ 5 REVIEW   1 per change, tiered by size/risk
                                       ├─ 6 FIX      fresh builder + re-review of the fix only
                                       ├─ 7 SHIP     PR (if asked), Closes #N
                                       └─ 8 LEARN    events → ledger; /learn promotes
```

The roles:

| Role | Who | Model · effort | Tools | Never |
|---|---|---|---|---|
| Orchestrator | main session | opus · medium | all | edits non-visual code, reads the whole diff |
| `rumo:scout` | agent | haiku (no effort) | Read, Grep, Glob, Bash (read-only use) | judges, gives opinions |
| `rumo:planner` | agent | opus · high | Read, Grep, Glob, Bash (read-only use), WebFetch, Write (the plan only) | edits code, decides product |
| `rumo:builder` | agent | **sonnet · high** | Read, Edit, Write, Grep, Glob, Bash | commits, leaves the worktree, fills a gap |
| `rumo:builder-opus` | agent | opus · medium | same as builder | same |
| `rumo:reviewer` | agent | opus · high | Read, Grep, Glob, Bash | edits, praises |

The agents live **in the rumo plugin** (`agents/`), versioned in `vkmtx/rumo-workflow` — not in
`~/.claude/agents`. Model and tools sit in the frontmatter: a dispatch without `model`
already lands on the right model.

## 3. Stages

### 3.1 align (`/rumo`) — what changes

- Same: grilling, one question at a time, `CONTEXT.md`/ADR the moment something resolves, a single window.
- **New — scout for facts.** "You gather the facts yourself" becomes: code questions
  ("where is X called?", "what is the test command?") go to `rumo:scout`, which returns
  `path:line` in < 300 words. The align window keeps conclusions, not dumps.
- **New — Definition of Ready**, checked before suggesting `/rumo ticket`:
  1. behavior described from the user's point of view;
  2. each acceptance criterion tagged `[cmd]` · `[julgamento]` (judgment) · `[visual]`;
  3. explicit out-of-scope;
  4. risk flag: does it touch **money · auth · data · security · prod**? (yes/no, which);
  5. new terms already in `CONTEXT.md`.

### 3.2 ticket (`/rumo ticket`) — what changes

- Same: tracer bullets, native blocking links, no interview, cut point.
- **New in the issue body:** criteria tagged `[cmd]/[julgamento]/[visual]` and a
  `## Risco` (risk) section (the DoR flag). Label `risk:sensitive` when the flag is yes.
- **New — slice size:** each T1 fits in **1 plan of ≤ 6 steps**. Bigger → slice it.
- A judgment ticket still closes via `Closes #N` without becoming a T2 — but it now **may**
  have delegated mechanical steps (see 3.3.3: `[julgamento]`/`[visual]` steps stay with the
  orchestrator, the rest goes to builders).

### 3.3 build (`/rumo build <target>`) — rewritten

Lanes 0/1/2 become a single rule: **the orchestrator always plans and dispatches; it executes
inline only what only the main session can see.**

Stays inline, with no planner or builder:
- trivial T0 (1 file, obvious change, ≤ ~30 lines) — a 1-line confirmation, as today;
- every `[visual]` step (render-verify and `design-taste` only see the main session);
- hard-bug diagnosis (`diagnosing-bugs` needs the red loop in hand).

Everything else goes through the 8 steps below.

#### 3.3.1 PLAN

The orchestrator dispatches `rumo:planner` with: the issue (`gh issue view --comments`), the
`CONTEXT.md`, the relevant ADRs and **the repo's lessons** (`docs/agents/lessons.md`, §4).
The planner returns the plan in the shape of `plan-template.md`, with **typed steps**:

```markdown
### Step 2: <imperative title>
- Files: src/orders/api.ts, src/orders/api.test.ts (create)
- Does: <exact behavior, named symbols, target shape when it matters>
- Test first: <case(s) that go red before the code>
- Verify: `pnpm test -- orders/api` → 2 new tests pass, 0 failures
- Type: cmd | visual | judgment
- Risk: none | money | auth | data | security
- Parallel with: step 3 (disjoint files) | —
- Model: sonnet | opus — reason in 1 line
```

**Model rule** (the planner applies it, the orchestrator checks it): `sonnet` only if all **4 conditions**
hold — (1) files named, (2) behavior described with no gap, (3) Verify is a command
with expected output, (4) Risk = none. Any failure → `opus`. `Type ≠ cmd` → orchestrator.

The orchestrator writes `plans/NNN-slug.md` (ephemeral, as today), stamps issue ↔ plan,
and runs the 2-axis drift-stop. It does not re-read the repo to check the plan — it checks only the form
(typed steps, a Verify on every step, scope = union of the Files).

#### 3.3.2 GATE (only when needed)

Stops and asks the user **only** if: the plan creates a new public interface (`tdd` seams —
a CLAUDE.md rule), some step has Risk ≠ none, or the planner returned an open
question. Shows the seams + risky steps in a table; the rest proceeds without asking.

#### 3.3.3 BUILD — waves

1. The orchestrator creates **one feature worktree** via `git worktree add
   ~/orca/workspaces/<repo>/<slug> -b feat/<slug> dev` (Orca's layout; it shows up in Orca).
2. Groups steps into **waves** by `Parallel with` (disjoint files, no dependency).
3. A 1-step wave → builder in the feature worktree. An N-step wave → each builder in a
   sub-worktree `<slug>-p<step>` off the feature tip; the orchestrator merges
   back (disjoint files → trivial merge; conflict → stop, `resolving-merge-conflicts`).
   Ceiling: **3 simultaneous builders** (memory: the Mac mini OOMed with parallel jest).
4. A `visual`/`judgment` step → the orchestrator does it inline in the feature worktree, after the
   wave it depends on.

Builder brief (fixed, lean): absolute worktree path · the whole step · the "Current state"
excerpts the step uses · relevant conventions + lessons · the contract:

> Edit only inside `<worktree>` and only the step's Files. Write the test first and watch
> it fail. Do not commit, do not push, do not launch an agent. If a decision is missing, stop and
> report what is missing — do not decide. Long output goes to a file; show `tail -40`.
> Answer in < 400 words: STATUS (COMPLETE|STOPPED) · what changed · commands run with
> pass/fail · deviations · open decisions.

#### 3.3.4 ACCEPT — per step, cheap

The orchestrator **does not read the diff** here (that is the reviewer's job). It:
1. `git -C <wt> status --porcelain` → a file outside the step = reject;
2. runs the step's **Verify** → failed = reject;
3. commits by path (`git add <step files>`), message in the repo's convention.

Rejection — a fixed ladder:
1. **REVISE** 1× in the same builder (SendMessage, warm cache), quoting the command and output;
2. **ESCALATE**: a fresh `rumo:builder-opus`, with the step + what failed (never retries sonnet);
3. **RE-PLAN**: the planner receives the step + both failures and rewrites the step (or the plan).
4. A second rejection after the re-plan → **BLOCK**, hand back to the user.

Each rung produces a learning event (§4.2).

#### 3.3.5 REVIEW — one per change, tiered

Fixed point = merge-base with `dev`..HEAD of the feature (a fixed SHA, recorded in the plan).

| Tier | When | Axes |
|---|---|---|
| **light** | diff < 50 lines and no `risk:sensitive` | Bugs (`code-review` medium) + Spec by the orchestrator's checklist |
| **standard** | everything else | Bugs (`code-review`) → Standards (`rumo:reviewer`) → Spec (`rumo:reviewer`) |
| **sensitive** | `risk:sensitive` or Risk ≠ none on some step | standard + `/security-review` |

New reviewer rules (from the studio):
- reviews the **fixed SHAs**, never the working tree; executes only in a `git archive` copy;
- `git diff --stat` first: a file outside the plan's scope **is a blocker**;
- **prove it or ask**: a finding without a concrete reproducible failure becomes a question, severity minor;
- style/formatting that lint already catches is not a finding; no praise;
- returns: findings (most severe first: `file:line` · failure scenario · proof · smallest fix),
  what was checked and is fine, what was **not** checked.

The axes stay sequential and never merged (the `review` 0.2 contract is kept).

#### 3.3.6 FIX — with re-review

Blocker/major → a fresh builder (model by the 4-condition rule) with the findings as
steps. Then, **re-review of the fix range only** + the original findings (reviewer, light
tier). This closes the studio's hole ("nobody re-reads the fix"). Minor/question → listed in the PR, not
blocking.

#### 3.3.7 SHIP

PR to `dev` with `Closes #N` only if asked this session (pr-base-guard already enforces it). PR
body: summary, a steps × model × result table, review findings and how they were handled.
Merge done by the user → delete the plan + the index line, `git worktree remove` the
worktrees, `git branch -d`, `fetch --prune`.

#### 3.3.8 LEARN — see §4

Before `DONE/PENDING`, the orchestrator records the run's events and prints the candidate
lessons (≤ 3 lines). It promotes nothing on its own.

### 3.4 standalone review (`review` skill)

Same tiers and same typed reviewer, outside the build. Model pinned on every axis.

## 4. /learn — learning from mistakes

Generalizes `design-taste`'s `taste-log` (which already works): **log cheaply, promote
on repetition, retire the rest.**

### 4.1 Where it lives

| Scope | File | Who reads it |
|---|---|---|
| Repo | `docs/agents/lessons.md` (committed) | planner (inline in the plan), reviewer (Standards axis) |
| Global | `~/.claude/learn/lessons.md` | `/learn` at promotion |
| Raw events | `~/.claude/learn/events.jsonl` (+ `.rumo/events.jsonl` in the repo, gitignored) | `/learn review` |

8 KB ceiling per `lessons.md` (checked by a script, §5). Over it → promote or archive.

### 4.2 Automatic capture (no model cost)

`build` appends one JSON line per event:

```json
{"ts":"2026-10-13T14:02Z","repo":"my-app","issue":42,"kind":"escalation",
 "step":"2","from":"sonnet","why":"Verify failed: null edge-case test","files":["src/x.ts"]}
```

`kind` ∈ `revise · escalation · replan · block · review-finding (severity) ·
scope-violation · hook-block · user-correction`. It also records per run: steps per
model, 1st try ok/failed, findings by severity — that is what measures whether the Model
rule is calibrated.

### 4.3 The command

`/learn` (skill `rumo:learn`, user-invoked):

- **`/learn`** (bare) — harvests the current session: your corrections ("não" (no), "errado" (wrong), a repeated
  instruction), hook blocks, failed commands, REVISE/ESCALATE. Proposes 1–5 lessons,
  each: *imperative rule in 1 line* · evidence (`event`/excerpt) · suggested destination.
  You approve/edit; it writes to the `lessons.md` of the right scope.
- **`/learn <text>`** — records the stated lesson, classifies the destination, done.
- **`/learn review`** — the improvement cycle:
  1. groups events + lessons by similarity;
  2. **2nd occurrence → promotion proposal** with a diff at the right destination:
     agent body (`agents/*.md`), a rumo reference, `plan-template`, CLAUDE.md,
     `design-taste`, or a **hook spec** when the rule is mechanical (becomes a PR in
     `~/.claude`/rumo, never applied without your ok);
  3. calibrates the Model rule: sonnet's 1st-try ok rate per step category;
     < 70% in a category → proposes sending that category to opus (or improving the brief);
  4. a single-occurrence lesson older than 60 days → `lessons-archive.md`;
  5. report: what was promoted, retired, and the fortnight's cost/quality.

Every promotion goes through `writing-for-agents` and a diff you approve — `/learn`
never rewrites an instruction on its own.

### 4.4 Transcript harvesting

`scripts/learn-harvest.py` reads `~/.claude/projects/*/*.jsonl` from the last N days and extracts
events the build did not see (sessions outside rumo): hook denials, `PostToolUseFailure`,
user messages that correct the previous turn. Output: lines in `events.jsonl`,
no model. Runs inside `/learn review`.

## 6. Expected cost by change size

| Change | Today (0.2) | 0.3 |
|---|---|---|
| trivial T0 | opus inline | same |
| medium, mechanical T1 | opus plans + 1 sonnet executor + 3 opus axes | fresh opus planner + 2–4 sonnet builders + standard review |

## 8. Implementation divergences (review of 2026-10-13)

1. **Parallel builders share the feature worktree** instead of sub-worktrees: this avoids one
   dependency install per builder. Safety comes from disjoint Files + a scope check
   by `status --porcelain` at every step.
2. **Plan = `<worktree>/.rumo/plan.md`**, never committed, no `plans/README.md` and no number;
   it dies with the worktree. `setup-repo` now creates `docs/agents/lessons.md` in place of the index.
3. **Events only in the global** `~/.claude/learn/events.jsonl` (a `repo` field), no copy in the repo.
   Kinds: `revise · escalate · replan · block · scope · finding` + `run`. A line without `ts` is
   discarded by `stats`.
4. **Harvest is a report**, it does not write events: `skills/learn/scripts/learn.py harvest`. The
   byte budget is `learn.py budget` (not a `scripts/context-budget.py`).
5. **`executor-contract.md` was deleted**; the contract lives in the body of `agents/builder*.md`.
6. **The `review_path` rule** became a condition of the light tier: a change to an agent definition or
   a SKILL's frontmatter is never "light".
7. **Additions**: a block after 2 fix rounds with a blocker; the sensitive tier is also triggered by a
   diff heuristic (auth, secrets, shell, crypto, money, public input, CI, native deps);
   in `/learn review`, a "≥ 2 sonnet failures in a category" trigger and the inverse calibration
   (opus ≥ 90% → propose sonnet).
8. **Proof of phases 1–2**: a headless run (`claude -p --plugin-dir`) in a toy repo —
   planner on opus, 3 builders on **claude-sonnet-5-5**, reviewers on opus (read from the `message.model`
   of the subagents' transcripts), 20 tests OK, a `run` event recorded.

## 9. 0.3.1 — hardening (pre-mortem of 2026-10-13)

Pre-mortem (18 failure modes) + disk/context measurement. What went in:

| Risk | Countermeasure |
|---|---|
| builder copies `.env` / runs a migration against a remote database | hook `~/.claude/hooks/worktree-guard.py` (cp/ln of `.env*` and migrations with a non-local URL denied inside `~/orca/workspaces`) + the builder contract |
| OOM from parallel tests | the same hook denies a 3rd simultaneous jest/vitest runner and reminds of the worker cap; the planner puts `--maxWorkers=2` in every Verify |
| builders contending for state in the shared worktree | builders do not install; Verify only after the whole wave; a step with a database/server/port runs alone; `PORT`/`TEST_DB` in the brief |
| a Verify that passes without proving anything | `skills/rumo/scripts/accept-step.sh`: passes, runs > 0 tests, and goes red without the step's code |
| the planner self-assesses risk | a path scan in the review; the scan beats the plan's `Risk: none` |
| review "ran" just because it started | `pr-base-guard` requires the `TIER:` line or code-review's completion notification |
| automation passing through the gate | no human → `BLOCKED: gate`, never the planner's defaults; no ship |
| `model` overriding the pin / uncapped cost | `workflow-model-pin` denies `model` on `rumo:*`; a warning from 15 subagents per session |
| code-review level stuck | an explicit level per tier |
| noisy calibration, secrets in events | `learn.py event` (schema, category enum, `env`, scrub, monthly rotation); calibration only with n ≥ 5; promotion across distinct sessions |
| a crash mid-wave, plan lost | `Done: <sha>` per step, resume requires a clean tree, a copy of the plan in `~/.claude/learn/plans/` |
| dead worktrees (11 GB measured) | `scripts/wt-gc.sh` (lists; `--apply` only removes clean MERGED/GONE ones; never automation) |
| source × cache × Codex diverging; a CLI update changing frontmatter | hook `session-drift.py` (SessionStart) + `scripts/smoke-agents.sh` |

Left for the user to decide: `cleanupPeriodDays` and pruning subagent transcripts (5.8 GB), and the first `wt-gc.sh --apply`.

0.3.1 divergences and additions (3-axis review):

- `gitleaks` is not installed on this machine: the secret scan is `learn.py scan` (the same patterns
  as the scrub), run on every write to `lessons.md` and in `/learn review`.
- `learn.py budget` also checks lines: `MEMORY.md` ≤ 200 lines and ≤ 150 characters per line,
  global `CLAUDE.md` ≤ 130 lines and ≤ 100 characters.
- `--runInBand`/`-i` does not count toward the test-run limit (single process, cheap) — on purpose.
- `review_ran` no longer accepts the mere invocation of `/security-review`; what counts is `TIER:` or the
  completion of code-review.
- `setup-repo` now adds `.rumo/` to the repo's `.gitignore` (besides the build's `info/exclude`).
- Additions: a `Category` field on the step (feeds the calibration), a check that Files have no glob/`..`,
  scope with `--ignored`, a builder waits and retries a test denied for concurrency, a new dependency
  becomes an `orchestrator` step, `wt-gc.sh` (lists only; `--apply` manual) and a warning above 4 worktrees.

## 10. 0.4 — critics, research and session data (2026-10-14)

Inputs: two critics (quality/security; cost/ergonomics), sourced research (Claude Code docs,
Cognition, Cursor, Anthropic advisor, Jules, OpenAI harness) and 7 days of transcripts (154 sessions).

| Change | Why |
|---|---|
| `build-guard` (hook): edits/commits in the main checkout denied after `/rumo build` (`#main-ok` allows them) | a real build made ~20 commits outside the worktree |
| `accept-step`: red only by assertion, `--expect`, `--red`, `--tests` (removed asserts, `.skip/.only`) | the "red" accepted "module not found"; a builder could weaken its own test |
| `issue-criteria.sh` + spec against the **issue**; a plan without `Done:` covering the commits = stale | the spec checked the planner's own plan |
| review axes = `rumo:reviewer` (bugs/standards/spec) in parallel, clean context | a fork inherited the builder's context, cost ~11M tokens and vanished without notifying; the wait dropped ~3× |
| replay of each blocker/major before the fix; a finding that does not reproduce becomes a question | the reviewer proved its own findings |
| a `rumo-review.ok` stamp in the git dir; `pr-base-guard` denies a PR/merge without a stamp for HEAD (`#sem-review`, docs-only) | the gate only warned and accepted a review of another HEAD |
| `rumo:visual-judge` (screenshots + design-taste + `[visual]` criteria only) and `render-verify` requiring 2 new images | the visual was judged by whoever built it |
| `check-verify` requires a verification that passed after the last edit; an edit via `sed`/heredoc counts | it counted a command run, not a command that passed |
| path scan also at the gate, and a narrower regex | the planner graded its own risk; `token`/`session`/`policy` gave false sensitives |
| fast path (a small or all-visual T1 skips the planner) and a ticketless build for "ready" prose | 7–9 touches for small changes |
| inline re-review < 30 lines; lesson candidates only when there was an event | cost and noise |
| `context-nudge` (300k/500k/800k), warnings for `general-purpose`+opus, fork and `sleep` ≥ 120 s; the guard ignores stopped/old runners | 65% of tokens with context > 300k; 73% of subagent tokens in general-purpose+opus; ~6 h in `sleep`; 10 concurrency blocks with a rising count |
| `/learn review` reads `fixed`/`dismissed` findings | Bugbot's idea: learn from what gets accepted or discarded |

Measure first (did not go in): the advisor pattern (Sonnet consults Opus — whether the command exists was not verified),
the standards axis on Sonnet, a token ceiling per build, a Codex second opinion on the sensitive tier.

Recorded exception (0.4 review): when **all** of a step's `--code` files are new, the only
possible failure without them is a load failure — `accept-step` accepts it as `red: load-only (new files)`.
