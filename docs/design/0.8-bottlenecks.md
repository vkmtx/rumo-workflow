# rumo 0.8 — measured bottlenecks (2026-10-28)

This came out of a usage analysis on 2026-10-28: `learn.py spend` over 3-, 7- and 30-day windows, `learn.py harvest`
and `stats`, and 4 read-only diagnoses done by Opus agents. Those agents read 2,372 transcripts, 1,493
events and 311 PRs. The scripts and raw data lived in an ephemeral session scratchpad and were not kept. The numbers
below are the baseline to measure against again.

## 0. Where we are (what works)

Weighted cost: input 1, cache read 0.1, cache write 1.25, output 5; Sonnet counts 0.6× and Haiku 0.2×.
Weeks start on Wednesday. Opus 5.5's list price was not checked; the unit is relative.

| week | sessions | builds | cost | main (% >200k) | workflow opus | cost/build |
|---|---|---|---|---|---|---|
| 09/30 | 107 | 0 | 1627 | 357 (74%) | 1008 | — |
| 10/14 | 196 | 26 | 733 | 435 (58%) | 39 | 28.2 |
| 10/21 | 311 | 111 | 1147 | 753 (51%) | 1 | **10.3** |

- **Cost per build:** fell 63%, with 4× more builds per week.
- **Workflow-subagent opus:** was 54% of subagent spend over 30 days and is now practically zero.
- **Builders' first-try success:** 95%, for both Sonnet (197/207) and Opus (365/384).
- **Review over 30 days:** caught 45 blockers and 235 major findings.
- **User corrections:** 8 in 390 sessions in the week.
- **Context ceiling:** `autoCompactWindow: 400000` holds; no session went past 368k.

The problems below are about **friction, integrity and calibration**, not architecture. The order follows severity.

## 1. Problems, root cause and fix

### P1 — The review stamp is self-declared (integrity) · priority 0

**Evidence**
- In `skills/review/SKILL.md:52`, the stamp is an `echo "$HEAD …" > rumo-review.ok` written by the
  orchestrator itself.
- `pr-base-guard.sh:185` only compares the SHA.
- Since 10/14 there were 74 real blocks (30 PRs without a stamp, 20 PRs with a stale stamp, 13 merges, 11 release PRs).
  After the block:
  - **55 of 73 were cleared by writing the stamp by hand, with no review in between;**
  - only about 11 had a real re-review.
- The 11 `dev→main` release PRs have no way to carry a stamp: the stamp covers the feature's HEAD, never
  `dev`'s HEAD.

**Root cause**
- The gate checks a file written by the very party it gates.
- The path the skill describes (re-stamp after the fix) is the same command as the shortcut.

**Fix**
1. Create `skills/review/scripts/review-stamp.sh`, the stamp's only writer.
   - Records `HEAD BASE tier axes-run` and the id of each reviewer run.
   - Requires verifiable evidence: for each axis of the tier, a `rumo:reviewer*` subagent transcript from the
     current session (`<transcript_path>/../<session>/subagents/*.meta.json`) whose prompt contains
     `RANGE: …<HEAD7>` or the fix range `stamp..HEAD`.
   - Inline-fix exception (<30 lines, outside the sensitive tier): allowed when
     `git diff --stat <stamp>..HEAD` gives <30 lines and no sensitive path; the stamp records `inline-fix`.
2. `pr-base-guard.sh`:
   - denies Bash that writes to `rumo-review.ok` (`>`, `tee`, `cp`, `mv`) outside `review-stamp.sh`;
   - a stale stamp denies with the order "run the fix-axis review over `<stamp>..HEAD`", not with "run the
     review".
3. Release PR `--base main --head dev`: passes when every commit in `main..dev` came from merged
   PRs (`gh pr list --state merged --search <sha>`), which already went through the stamp. Otherwise it denies and
   lists the orphan commits.
4. Codex mirror: the hook runs through `claude-bridge.py` (the Codex mirror setup), so confirm with
   the smoke test.

**Files**
- `skills/review/SKILL.md` §Stamp
- `skills/review/scripts/review-stamp.sh` (new)
- `~/.claude/hooks/pr-base-guard.sh` (outside the repo; back it up first)
- `~/.claude/hooks/tests/pr-base-guard.test.sh`

**Verification (pass/fail):** new cases in `pr-base-guard.test.sh`, all of which must pass:
- `echo x > .git/rumo-review.ok` → denies;
- `review-stamp.sh` without a reviewer transcript → exit ≠ 0;
- with a reviewer fixture for HEAD → writes, and `gh pr create` passes;
- a new commit after the stamp → denies, citing the fix axis;
- a release PR with every commit from merged PRs → passes; with an orphan commit → denies.

**Measure in production:** over 7 days, 0 stamp writes outside the script (grep over the transcripts).

**Risk:** medium. It touches the hook that protects merge/deploy, so it is tested before installing and there is a backup in
`~/.claude/backups/hooks-<date>`.

### P2 — `learn.py stats` breaks and the event schema has drifted · priority 0

**Evidence**
- 3 `run` events recorded `steps`/`first_try` as a number or text (lines 321, 991 and 1119). `stats`
  breaks with a `TypeError` at `learn.py:216`.
- 40 lines fail the current `validate_event`. The deviations:
  - categories outside the vocabulary (`layout`, `ui`, `visual`, `authz-race`, `"auth, data-model/risk"`…);
  - `severity` `medium`/`low`;
  - `model` `ci`/`orchestrator`.
- Lines 919–920 got in without going through the validator; nobody knows how.
- The `run` format exists only in prose, in `build.md:132`. The example at `build.md:128` ends in `…`.
- The list of repeated causes is inflated: paired rounds record the same `why` twice (85 pairs).

**Fix**
1. `validate_event` for `run`:
   - `steps`/`first_try` are objects `{sonnet|opus|haiku|orchestrator: int≥0}`, with `first_try ≤ steps`;
   - `by_category` keys in the format `<CATEGORY>[/risk]` with `{steps, first_try}` cells;
   - `findings` with keys `blocker|major|minor|question`.
2. For `finding`: `severity` required and within the vocabulary; `model` accepts `orchestrator`; `ci` is rejected
   (a CI failure becomes a `revise` with `env`).
3. Decide on **one** visual category. Today 19 runs use `ui`/`layout`/`visual`/`style`, so either
   `visual` enters the vocabulary or everything becomes `ui-logic`. Recommendation: **add `visual`**, because P5
   needs to measure exactly that.
4. `stats` now skips and warns: it drops what `validate_event` rejects and prints
   `skipped N malformed (lines …)`. It also dedupes paired findings by `why` when counting causes.
5. A complete `run` event example in `build.md` §9, with no ellipsis.
6. Normalize the history with a single script that produces a copy and a backup. The diff goes to the user
   before the file is replaced, because the log is the calibration source.

**Files**
- `skills/learn/scripts/learn.py`
- `skills/learn/tests/`
- `skills/rumo/references/build.md` §9

**Verification (pass/fail)**
- `learn.py stats --days 30` exits 0 on the real log and prints `skipped 3`.
- `echo '{"kind":"run","repo":"x","steps":11}' | learn.py event -` exits 2.
- The learn tests pass.

**Risk:** low.

### P3 — The test gate counts PIDs, not runs (throughput) · priority 1

**Evidence (7 days)**
- 641 denials across 299 transcripts, the #1 block.
- `count_runners` (`worktree-guard.py:262-284`) counts every PID whose argv contains `jest`/`vitest`, across the
  whole machine, without grouping the process tree.
- A single run becomes 2 to 5 PIDs:
  - `pnpm exec vitest` = shim + node;
  - `accept-step.sh` = zsh + bash + `bash -c` + pnpm + node, and it counts even while running only typecheck or
    lint.
- **With a ceiling of 2, the effective ceiling is about 1.** At the moment of denial, 375 of 641 had one real run
  and 182 had zero; only 13% had 2 or more.
- There are ungated paths that still count: `accept-step.sh` (the command starts with `bash`) and `--runInBand`
  (used 36 times as a bypass). That is why denials show 3 to 9 processes.
- **Cost:** 1,277 turns (about 155M context tokens) spent on `ps`, `kill`, `sleep` and retry.
  Median wait 40 s, p90 7.7 min; about 15 h in total.
- Stuck processes are a minor factor: 7 runners over 10 min, all real long jest runs from
  a mobile app project.

**Root cause:** counting by PID, plus ungated paths, plus waves of 5 (build.md:77) contending for what is,
in practice, a single slot.

**Fix (keep the ceiling at 2)**
1. **Count logical runs.** Only the main jest/vitest node process, collapsed by ppid. Package-manager
   and shell wrappers do not count.
2. **Wait before denying.** The hook polls every 3 s for up to about 50 s before denying
   (adjust the hook timeout in settings). The 40 s median wait disappears, with 0 turns spent.
3. **Close the bypass.** `--runInBand`/`-i` and `accept-step.sh` fall under the same limit; `--runInBand`
   stays exempt only from the workers warning.
4. Fix the warning text at `:352`, which still says "up to 3 builders".
5. Builders run only the step's test file; the full suite only at the end of the wave (`builder*.md`,
   `build.md` §3).
6. Check whether Vitest 5 still accepts `--poolOptions.threads.maxThreads`, the flag `builder.md:24`
   says to use (context7).

**Prerequisite:** measure the total RSS of the runner trees during a wave on a large ERP project (sampling with `ps`
every 5 s). Two simultaneous real runs must fit in 16 GB with headroom, given the OOM history.
If they do not, the ceiling becomes 1 logical run with waiting, which is still better than today.

**Files**
- `~/.claude/hooks/worktree-guard.py` + test
- `agents/builder.md` and `agents/builder-opus.md`
- `skills/rumo/references/build.md` §3
- `skills/rumo/references/wave.md` §38-40
- the hook timeout in `~/.claude/settings.json`

**Verification (pass/fail)**
- `worktree-guard.test.sh` with `WORKTREE_GUARD_PS` fixtures taken from the real trees:
  - one `pnpm exec vitest` → allows;
  - one `accept-step` tree → allows;
  - two runner nodes → denies;
  - `--runInBand` with 2 running → denies.
- Re-measure in 7 days: fewer than 100 denials, and fewer than 5% of them with ≤1 logical run.

**Risk:** medium, because of RAM. That is why the measurement comes first.

### P4 — False positives in check-verify and render-verify (friction) · priority 1

**Evidence (since 10/21)**
- 230 Stop blocks: **103 are false positives**, 103 are true and 24 ambiguous.
- check-verify:
  - 47 blocks from scratch files written as `$VAR` or a relative path (`$TMPDIR/done.py`, `../../outline.py`).
    The hook only recognizes literal `/scratchpad/`, `/tmp` and `/var/folders` paths (`check-verify.sh:142`).
  - The verification regex (`:39-44`) does not recognize `pnpm --filter X test`, `pnpm -C … typecheck`,
    `exec biome check`, `playwright test`, `pnpm e2e` or `node --test`.
  - `.py`/`.sql` get an npm check, and `.css` edited via `sed` falls into check-verify.
- render-verify:
  - 16 blocks on video compositions in a video project;
  - 16 on scratch/Artifact;
  - 7 on print HTML in ~/Documents;
  - 3 on downloaded router HTML;
  - 3 on a temporary copy.
- Cost of the false positives: about 340 turns and 2.2 h in total.

**Fix**
1. Only count a file inside the session directory's `git rev-parse --show-toplevel`. `$VAR` is expanded
   when possible and, if not, treated as scratch. A relative path is resolved against the `cd`s
   the hook already collects (`:100`). Applies to both hooks.
2. Widen the verification regex with `pnpm (--filter|-C) X <check>`, `exec biome`, `playwright test`,
   `e2e`, `accept-step.sh` and `node --test`.
3. Per-language check: `.py`/`.sql` do not get the npm gate; css stays with render-verify only.
4. A per-repo marker `.claude/no-render-verify` for video projects and print documents (decision D4).

**Files:** `~/.claude/hooks/check-verify.sh`, `~/.claude/hooks/render-verify.sh` + tests.

**Verification (pass/fail)**
- Re-run the fixed hooks against the 230 recorded blocks, with each transcript cut at the point
  of the block (an adapted version of the analysis's block-replay script).
- Passes when ≥90% of the false positives stop blocking **and** all 103 true ones keep
  blocking.

**Risk:** low. A real write to the repo made via `$VAR` would slip through.

### P5 — Visual work misses on the first try (quality) · priority 1

**Evidence**
- The orchestrator's first-try success: `ui-logic/risk` 5/12 = 41%, `ui-logic` 10/14, `ui` 3/5,
  `visual` 0/2. It is the worst category in the system. Sonnet on `ui-logic` gets 59/61.
- **34 of 56 visual-judge rejections cite a lesson or rejection already recorded:**
  - brand color as text (13);
  - native controls without design (6);
  - touch target <44px (6);
  - flat layout (6);
  - sticky bar over the content (4, recurring).
- The orchestrator loads design-taste (64 times in the ERP project), but nothing forces it to check the rules
  before rendering.
- The ERP project's "overview" page:
  - the judge's brief on #82 asked to "follow the project's design contract" plus birthdays, and the judge gave **PASS**;
  - no criterion said the page is a billing dashboard;
  - the complaint became ticket #110 instead of a fix, so the user repeated it 3 h later;
  - dataviz was never loaded in a session of that project.
- The judge is not the problem (84 PASS, 55 FAIL). But 77 runs ended without a parseable `VERDICT` line.

**Fix**
1. **Visual brief before the 1st edit:** `.rumo/visual-brief.md` with
   - the page's purpose;
   - a content inventory (what has to appear);
   - the dominant element;
   - a reference image (approved prototype or competitor);
   - the taste-log rules and the project contract rules that apply (the project's visual-prototype research
     doc, when one exists).

   The visual-judge receives the same file (`build.md` §2, `agents/visual-judge.md`).
2. **Mechanical `visual-lint`** (Playwright) as a `[cmd]` gate before the judge:
   - targets ≥44px at 390;
   - no horizontal scroll;
   - sticky header opaque and with no content underneath;
   - no native `date`/`time`/`select`;
   - screenshot mtime later than the last edit.

   Covers about 20 of the 56 FAILs, deterministically.
3. **Ticket with a page-level visual criterion:** a block that goes into a shared page requires a
   `[visual]` criterion for the whole page, plus a reference (`ticket.md`, `align.md`).
4. **Dashboard → dataviz:** a metrics page loads the dataviz skill along with design-taste
   (`build.md`, `SKILL.md`).
5. **The user's visual complaint about a just-delivered build:** becomes a fix in the same build, not a new ticket.
   It becomes a ticket only if it is new scope (`build.md` §FIX).
6. The visual-judge now **always** ends with `VERDICT: PASS|FAIL` (`agents/visual-judge.md`).

**Files**
- `skills/rumo/references/build.md` §2/§FIX
- `skills/rumo/references/ticket.md` and `align.md`
- `agents/visual-judge.md`
- `skills/rumo/scripts/visual-lint.*` (new)

**Verification (pass/fail)**
- A fixture with a 40px button and a translucent sticky → `visual-lint` exits ≠ 0; the fixed version → 0.
- Over the orchestrator's next 10 visual steps: first-try success ≥70% (today 41%), and at most 2 FAILs
  citing an already recorded lesson.

**Risk:** medium. `visual-lint` needs per-stack selectors, and RN/Expo web is harder.
Start with the Next projects.

### P6 — Review: calibration, open findings and security · priority 1

**Evidence**
- **The standards experiment (rule in `skills/review/SKILL.md`, deadline 2026-11-03):** 77 paired
  builds, 515 findings.
  - Fixed: Sonnet 74 vs Opus 100 = 74%. The rule asks for ≥80% → **fails**.
  - Dismissals: 10% vs 4%, within Opus +10 → passes.
  - Severity: Opus caught 4 blockers and 10 majors that were fixed; Sonnet, 1 and 6.
  - **The rule sends standards back to Opus.**
- **Open findings (476):** 455 minor, 15 major, 2 blockers. They go to the PR body by design
  (`build.md:113`). 136 of 311 PRs list these findings; **only 2 open a follow-up issue**. After the
  merge, nothing brings them back. The 2 open blockers and 15 open majors contradict `build.md:113` itself.
- **`/security-review`:** 216 runs as general-purpose opus (median 594k tokens, about 220M in
  total). It diffs against `origin/HEAD`, which has already forced a manual workaround (a PR in the ERP project). `security`
  already exists in learn's AXES, but not in `reviewer.md`.
- **"dismissed ×28 ui-logic":** this is noise, because `category` belongs to the step, not the finding. But
  **"dismissed ×20 refactor"** is a real signal: 15 of 20 are pre-existing duplication flagged by
  standards·sonnet.
- **Fix re-review:** 188 runs, 167 of them on Opus. About 64% of builds land in the sensitive tier, which
  suggests the path filter is too broad.

**Fix**
1. On 2026-11-03, apply the rule: standards goes back to `rumo:reviewer`, and `reviewer-sonnet` keeps only
   the fix axis outside the sensitive tier. This ends the pairing, saving about 1.5% of weekly
   cost.
2. An open major or blocker finding **blocks the stamp**, unless the user explicitly waives it.
   Open minors and questions become **one follow-up issue per PR**, with the PR linked (`build.md:113,134`).
3. A dismissal gains a `reason` field (`pre-existing|by-design|owner-waived|wrong`), and `stats` groups
   axis × reason. Standards no longer flags pre-existing duplication outside the diff (`reviewer.md`).
4. A typed `security` axis in `rumo:reviewer`: fixed RANGE, replay and log. It replaces `/security-review` in the
   sensitive tier; the built-in command stays available standalone.
5. Measure, before changing anything, which paths push builds into the sensitive tier. Only then tighten the filter.

**Files**
- `skills/review/SKILL.md`
- `agents/reviewer.md` and `agents/reviewer-sonnet.md`
- `skills/rumo/references/build.md` §REVIEW/§9
- `skills/learn/scripts/learn.py` (reason)

**Verification (pass/fail)**
- `grep reviewer-sonnet skills/review/SKILL.md` shows only the fix axis.
- The next merged PR with an open minor links an issue.
- A sensitive-tier review logs `axis:security, model:opus` with a RANGE equal to the merge-base.

**Risk:** low for items 1–3, medium for item 4.

### P7 — Cost: the planner over-explores, the main session runs long · priority 2

**Evidence**

*Planner:* 8.7% of weekly cost, median 41 turns.
- 84% of turns are exploration, one `sed -n`/`cat` per call (91% of turns with a single tool).
- The 1st `Write` comes at turn 37 of 41.
- **18 of 94 planners hit maxTurns 50** without writing, and the orchestrator had to tell them to stop.
- Median plan of **51k characters** (p90 64k), inflated by the "current state" excerpts.
- plan-check is **not** the problem: only 3 of 86 failed on the first try.
- Cost follows turns (r=0.86), not repo size (r=0.01).

*Main session:* 64% of cost.
- Turns between 200k and 400k of context = **50% of the main session's cost, or 32% of the week's total.**
- The 120k nudge only fires on `/rumo build|wave`. 5 of the 10 most expensive sessions are not builds (video,
  ops), and one was a CRM hub project that did a clone, VPS work, a prototype and reviews in the same window.
- Wave orchestrator: polling = 34% of one session's cost (the ERP project).

**Fix**
1. **Planner:**
   - read in batches (several `sed -n` excerpts per call);
   - the orchestrator hands over `rumo:scout` facts in the brief when it already has them;
   - maxTurns 50→35 with "write by turn ~28";
   - never read the source of `plan-check.sh` (`agents/planner.md`, `build.md` §3.2).
2. **Plan ceiling at ~20k characters:** excerpts become a signature plus a few lines. `plan-check.sh`
   gains a size check (`plan-template.md`).
3. **Main session (D1):**
   - `autoCompactWindow` 400k→250k in the global settings;
   - context-nudge at 200k for **any** prompt (not only build), suggesting a handoff and `/clear`;
   - never blocks, only warns.
4. **Wave:** one status script per wake-up, instead of several reads (`wave.md`).
5. Screenshots: the judge reads them; the main session reads them only when it needs to judge (about 2%).

**Files**
- `agents/planner.md`
- `skills/rumo/references/build.md` §3.2
- `skills/rumo/references/plan-template.md`
- `skills/rumo/scripts/plan-check.sh`
- `skills/rumo/references/wave.md`
- `~/.claude/settings.json` and `~/.claude/hooks/context-nudge.py` (D1)

**Verification (pass/fail), with `learn.py spend --days 7` one week later**
- `rumo:planner · opus`: from 480.6M / 42 turns to ≤340M and ≤30 turns.
- Planners at the turn ceiling: ≤5% (today 19%).
- "main session turns at >300k": from 17% to ≤3%.
- Tokens per build: −8% or more.
- **Quality guard:** first-try success and blockers in `stats` do not get worse.

**Estimated savings:** P7 10 to 14% of weekly cost, plus 1.5% from P6.1. An estimate, not measured.

**Risk:** low to medium. Compacting earlier loses context mid-task.
